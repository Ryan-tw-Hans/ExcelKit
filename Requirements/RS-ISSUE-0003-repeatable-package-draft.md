# 可重複打包腳本與 Skill 方案草案｜ISSUE-0003

狀態：待使用者確認。執行者 Codex（PM、SA、系統整合、維運、測試與軟體，均為自查）。本需求延續 ISSUE-0003，沿用 L3：涉及建置及固定發布資料夾的流程、版本一致性與回復；不降級。使用者明確要求建立流程 skill，可在專案 `.agents/skills/` 建立專用 skill；不因此授權加入 Git、提交、推送、正式發布、部署或合併。

## 目標與事實

後續 AI agent 以固定入口建立 ExcelKit 測試版，產出可追溯的內容清單與證據。現有 src/Excelopen/Excelopen.csproj 的 Release 建置會複製到 publish，且 README 明載不自動清除舊檔；Installer/Rebuild-Setup.ps1 僅編譯 Config 及目前 publish 素材。DLL 版本在 csproj、Class1.cs，安裝器版本在 .iss，兩者可能合法不同；需分別標示並檢查，不能宣稱相同版本即位元組一致。

## 建議方案

1. 建立專案交付腳本 `Installer/Package-ExcelKit.ps1`，固定以專案根目錄為基準、不依執行時目前目錄。由呼叫者明確提供或由腳本依既有正式基準 1.2.4 和台北時間產生唯一的測試版安裝器版本；遇到同版輸出即停止。DLL 的組件／檔案／資訊版本以已核准的原始碼為準，腳本不靜默更改 DLL 版本或正式基準；若 csproj 與 Class1.cs 的公開版本矛盾則停止並要求先解決。
2. 在工作區內建立每次獨立、空白的暫存工作目錄，從明確的原始碼、`Reference/Manual`、`Reference/Media`、`Reference/VBS`、`Reference/PowerShell`、`Reference/LabVIEW`、`Reference/Examples-README.md` 與 Installer 設定建立清單，建置 net472／net10.0 並檢查每個必要輸入；不從既有 publish 混入殘留檔，不修改、不刪除現有素材。需要檢查工具、系統架構及執行中的目標，無法安全辨識或目標正在運行時停止，保留工作區與錯誤記錄。
3. 將本次選定的安裝器版本寫入暫存 .iss，從實際待打包 DLL 產生且驗證 PackageMetadata.iss，使用指定的 Inno Setup 編譯器；核對產物內可讀的產品版本、DLL 雜湊及來源清單後，以不覆寫既有檔案的方式輸出到 `publish/Installer/Setup/`。記錄工具版本、版號、輸入／輸出 SHA-256、時間、步驟與測試狀態，保留日誌與清單；失敗不覆寫既有正式或測試成果，不自動清除使用者資料。
4. 提供 dry-run／預檢模式：只讀取、列印預計操作及必要檢查，不寫入發布資料夾或執行安裝。正式打包前需通過預檢；腳本本身不啟動安裝器、不註冊 COM、不部署。
5. 建立 `.agents/skills/excelkit-package/SKILL.md`，說明何時使用、所需輸入、命令、結果判讀、版本與授權界線，以及必須依 pm-intake／build-release／test-plan 和 IssueLog 登記的條件；不把 skill 加入 Git，除非使用者另有指示。

## 適用性與主要風險

- 架構：適用，新增打包入口、暫存及輸出與失敗恢復邊界；採隔離 staging＋明確清單優於重用可能有殘留的 publish。
- UI／視覺：不適用，不變更應用或安裝精靈畫面；腳本為命令列。
- 資料庫：應用資料庫不適用；IssueLog 只依既有流程記錄，腳本不改 schema。
- 系統整合：適用，需核對 .NET SDK、Inno Setup、目標框架、來源與環境差異。
- 維運：適用，需驗證重複執行、輸出衝突、缺檔、建置失敗與人工恢復；不可終止未確認的其他程序。
- 一致性指固定流程、精確輸入清單、版本及雜湊可追溯；建置時間、工具版本、時間戳或壓縮器可能使安裝檔位元組不同，不承諾跨環境逐位元重現。

## 測試與驗收草案

- 使用隔離測試工作目錄測試 dry-run 不產生發布檔，缺少工具／必要檔案、版本不一致、目標已存在及程序執行中會安全停止。
- 實際測試完整建置和編譯；確認淨空 staging 不含舊檔，兩框架、手冊／媒體／範例、DLL 版本及雜湊、安裝器版本與清單相符；重複執行不覆寫。
- 以失敗注入或受控缺檔驗證錯誤結束碼及既有成果不變；驗證 skill 的格式、指向的腳本與命令。GUI、COM、安裝／升級／移除仍依既有 ISSUE-0003 計畫，不能把打包測試當成實機驗收。
- 輸出前檢查目前安裝程式是否執行中；不能安全關閉則停止。產出僅為測試版；不自動提交、合併、部署或更新正式版。

具體參數名稱、所需工具版本、staging 邊界、輸出與回復細節待軟體工程師依本方案落實並記錄；若發現無法保護既有成果或需要不可逆清理，停止並回報 PM。
## 2026-11-16 補充：進版對應與安裝後驗證

使用者要求未來程式進版時安裝程式顯示正確版本，並詢問安裝後可否以腳本確認。本草案補足下列功能，與前述打包方案一併待確認：

1. 將 DLL 公開產品版本（csproj Version／InformationalVersion 及 Class1.cs GetVersionInfo 所使用的版本）、DLL AssemblyVersion／FileVersion、安裝器 AppVersion 分別列出。打包前確認原始碼中的公開產品版本一致；從實際編譯的 DLL 取得組件／檔案版本及 SHA-256，產生安裝器使用的資料並比對。腳本需檢查版本與本次指定的產品版本／測試版策略相容，版本不一致即失敗，不靜默猜測或改寫已核准的程式碼。安裝器可顯示本套件的 DLL 版本、安裝器版本與既有 DLL 比較結果；不強迫不同用途的版本字串完全相同。若需要變更 DLL 的公開版本或正式版基準，先依專案進版流程處理並記錄。
2. 打包時產生對應本次產物的安裝驗證資料，至少含安裝器版本、DLL 公開產品版本、組件／檔案版本、必裝檔案與各可選項的檔案雜湊清單。安裝器安裝時需保存能辨識本次已選 COM 位元及可選項的資訊，以供日後檢查；升級時需區分新選項與先前保留的檔案，不把未選項目或遺留資料誤判為安裝錯誤。清單及選項資料的保存、升級與解除安裝影響須納入設計與隔離測試。
3. 提供獨立的安裝後驗證腳本，以唯讀方式檢查指定／可確認的安裝目錄、必要及已選檔案的存在與雜湊、安裝器版本及選取的 x86／x64 COM 註冊與 DLL 路徑／版本。使用者層覆寫、找不到預期清單／選項資訊、存取拒絕或版本不一致時，回報「無法確認」或「失敗」，不可猜測或顯示通過；輸出通過／失敗／未執行與證據，不修復、不重新註冊、不移除任何檔案。
4. 另提供明確啟用的功能檢查：在適用的 x86／x64 客戶端建立 COM 物件，呼叫 GetVersionInfo 與既有基本讀寫煙霧測試，僅使用隔離暫存測試資料，並列出可能的程序及日誌副作用。只檢查使用者選擇安裝的位元數；不直接在正式環境自動啟動 COM，不操作使用者工作簿、印表機或既有資料。無法執行時記錄未執行；實際可用性仍須在指定目標環境驗收。
5. 測試計畫增加：新版與舊版版本對照、DLL 原始碼版本不一致、檔案被修改或遺失、已選／未選組合、x86／x64 註冊、升級殘留、清單或權限不足，以及選用 COM 測試的正常／失敗情況；驗證腳本本身不變更既有安裝及使用者資料。
